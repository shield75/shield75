### 👨‍💻 About Me

I'm a **QA Automation Engineer** who lives at the intersection of **web and mobile testing** — designing frameworks that don't just click buttons, but think about *what breaks, why it breaks, and how to catch it before production does*.

- 🔭 Currently deep in **Playwright + Maestro**, wiring both into **MCP (Model Context Protocol)** servers so AI agents can drive tests through structured, accessibility-aware context instead of brittle screenshots.
- 🧪 Background rooted in **Selenium WebDriver**, so I understand both *why* modern tools exist and *how* to debug them when the abstraction leaks.
- 📱💻 I build **unified automation strategies** — one CI pipeline, one reporting layer, two engines (Playwright for web, Maestro for mobile) running in parallel.
- 🌱 Exploring **agentic QA** — where LLM-driven agents propose test flows, self-heal locators, and triage flaky failures.
- 💬 Ask me about test architecture, flaky test debugging, or how to convince your team to invest in automation ROI.

### 🎯 Where I Bring the Most Value

<table>
<tr>
<td width="50%" valign="top">

**🌐 Web Automation — Selenium & Playwright**
- Deep Selenium WebDriver fundamentals: explicit waits, custom `ExpectedConditions`, Page Object Model, and grid-based parallel execution — the kind of knowledge that doesn't expire when the tooling trend shifts.
- Playwright as the daily driver: auto-waiting, network interception/mocking, trace viewer for post-mortem debugging, and multi-browser (Chromium/Firefox/WebKit) execution from a single API.
- **Playwright MCP** — running Playwright as a Model Context Protocol server so an AI agent can inspect the live accessibility tree, decide the next action, and execute it — turning exploratory testing and self-healing locators from a manual chore into an agent-assisted workflow.

</td>
<td width="50%" valign="top">

**📱 Mobile Automation — Appium & Maestro**
- Appium for the deep end: native + hybrid app coverage across Android/iOS, driven by the WebDriver protocol when I need low-level control over gestures, contexts, and device capabilities.
- **Maestro** for fast, YAML-driven mobile flows — readable test files that product and QA can both review, with built-in retry-ability that shrugs off animation timing flakiness.
- **Maestro MCP** — exposing Maestro's flow engine to an AI agent so it can drive a mobile UI conversationally, validate a flow in natural language, and generate/adjust `.yaml` test flows on the fly.

</td>
</tr>
</table>

**🔗 The bigger play — Unified Cross-Platform Automation:**
Rather than treating web and mobile as separate silos, I run **Playwright and Maestro side-by-side** in the same CI pipeline — shared test data, shared reporting (Allure/Xray), and shared triage process. The goal: one PR, one automation gate, whether the change touches a React web app or its React Native/native mobile counterpart. Layering **MCP agents** on top of both means an AI assistant can be pointed at either surface and reason about UI state the same way — closing the gap between "AI can browse the web" and "AI can test *your* app."
